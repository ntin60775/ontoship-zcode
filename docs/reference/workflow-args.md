# Аргументы CreateWorkflow — транспорт не режет, abort несёт причину

Готча из диагноза «хост обрезает args» (2026-10-03,
[репро-отчёт](../plans/queue-2/09-diagnose.md)): неделя ложных гипотез о
«капе на транспорте» — на деле строка была невалидным JSON ещё у вызывающего.

## Факты

- **Хост НЕ режет строковые args.** Транспорт доставляет мульти-килобайтные
  строки байт-в-байт — проверено пробами до 12 414 символов (~24.8 КБ UTF-8) в
  одном аргументе и ~33 КБ суммарно (`dwfrun-eb1e4a99`, маркеры целы,
  JSON парсится). Ни байтового, ни символьного капа, ни капа на суммарный
  payload не найдено.
- **«Не распарсились» = битый JSON у вызывающего.** Если workflow-скрипт падает
  на `JSON.parse` аргумента — строка дошла ровно такой, как была отправлена:
  ищи ошибку сборки у вызывающей сессии (ручная сериализация вместо
  `JSON.stringify`), а не в транспорте.
- **`type: json` — структурное значение, а не строка.** json-типный аргумент
  передавай значением (массив/объект), а не заранее сериализованной строкой;
  при неизбежной строке — `JSON.parse`-проверка до сабмита.

## Контракт abort-сообщений

Оба наших workflow (`challenger`, `onto-doc`) при непарсящемся JSON-аргументе
обязаны нести в abort **три вещи**:

1. `e.message` парсера — ошибка с позицией («Unexpected token … at position N»);
2. полученную длину строки;
3. хвост строки (~80 символов) — по нему «обрезано» (нет закрывающих `]}`)
   и «битый синтаксис» различаются сразу; голова одна и та же у обоих случаев.

Голова строки тоже включается (при длине > 80), но различает случаи именно
пара «хвост + позиция ошибки».
