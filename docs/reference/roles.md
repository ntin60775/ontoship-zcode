# Роли subagent-моделей (reviewer, challenger)

**Роль** — имя, которое говорит, на какой модели выполняется субагентный шаг
(`subagent_model` в `CreateWorkflow`). Плагин поставляет две роли (`defaults/roles.md`):

| роль | потребитель | что делает |
|---|---|---|
| `reviewer` | `/ship`, шаг 6 (`skills/ship/SKILL.md`) | независимое read-only ревью дифа тикета |
| `challenger` | grilling (`skills/grilling/SKILL.md`) | red team по черновым решениям |

Смысл ролей в том, что проверяющий шаг работает на **другой** модели, чем сессия:
ценность независимого ревью и red team исчезает, если шаг молча садится на модель
автора. Отсюда два правила ниже — слои и fail-closed.

## Три слоя разрешения

```
plugin default   <plugin>/defaults/roles.md      в потребителе: <repo>/.zcode/defaults/roles.md
user global      ~/.zcode/ontoship/roles.md      (дом переопределяет $ONTOSHIP_HOME)
project          <repo>/.zcode/ontoship/roles.md
```

Разрешение — от общего к частному, **слияние по имени роли**: более специфичный слой
заменяет роль только если сам её определяет; проектный `reviewer` не прячет
пользовательского `challenger` (`resolve()` в `skills/roles/roles.py`). Plugin-слой —
это дефолты автора (сейчас хост-план Z.AI: обе роли `GLM-5.3-Flash`, `level: max`);
user-слой перекрывает их для всех проектов, project-слой — для одного репозитория.

У каждой разрешённой роли есть провенанс — `_source` (`plugin-default` | `user` |
`project`) и `_file`; виден в `roles.py resolve [--json]`. Дашборд `/roles` помечает
⚠ роли из project-слоя: они затеняют пользовательский выбор.

## Формат файла слоя

Frontmatter с блоком `roles:`, два уровня вложенности:

```yaml
---
roles:
  reviewer:
    model: account:zai-individual-coding-plan/GLM-5.3-Flash
    level: max            # опционально; уровень резонинга той же модели
---
```

Парсер строгий, любая вольность — ошибка, а не молчаливое игнорирование
(`parse_roles` в `skills/roles/roles.py`):

- имя роли — `^[a-z][a-z0-9-]*$` с отступом ровно 2 пробела, ключи — только
  `model` (обязателен) и `level`; значение `level` парсер не валидирует — regex
  `^[a-z][a-z0-9-]*$` применяет `set` к аргументу (`_split_model`); парсер
  принимает отступ ключей 4 и больше, канонический вывод `set` — ровно 4;
- файл обязан открываться `---` и закрываться вторым `---`; незнакомая строка
  или пустое значение — `RolesError` с файлом и номером строки, роль без
  `model` — с файлом;
- `set` перезаписывает слой канонически: имена ролей по алфавиту, `model` + `level`.

Слои правит только `/roles` (см. `commands.md`), не руками.

## Чтение и запись

Скрипт — `skills/roles/roles.py` (`resolve` / `set` / `unset` / `version`), UI —
скилл `/roles` (`skills/roles/SKILL.md`). Дефолты глаголов асимметричны и это
осознанно:

- `set` пишет **user-слой** (действует на все проекты); project-слой — только явный
  `--project`. Модель проверяется по **ListModels** хоста (id существует, не
  `disabled`, `$level` есть в `reasoningLevels`); неизвестная — стоп, ничего не
  пишется, дальше смоук микроворкфлоу на новой роли.
- `unset` снимает **project-слой** (частый случай — убрать затеняющий оверрайд);
  `--user` — пользовательский.
- Голый `set` без `$level` заменяет запись роли целиком и молча теряет уровень,
  унаследованный с нижнего слоя — в `set` всегда указывай явный `$level`.

## Fail-closed

Две независимые проверки, обе обязательны:

1. **Резолвер.** Отсутствующий файл слоя — норма (`{}`), **битый — ошибка**:
   эффективная конфигурация была бы недостоверной, поэтому `resolve` падает с
   `[FAIL]` и кодом 1, а `set`/`unset` отказываются писать в битый слой
   (`load_layer`, `_write_layer` в `skills/roles/roles.py`).
2. **Потребитель роли.** Перед субагентным шагом: `roles.py resolve --json`,
   взять `model$level` роли, сверить с **ListModels**. Любое несовпадение —
   **остановить шаг** с диагностикой (роль, ожидаемый id, файл слоя для правки).
   **Никогда не откатываться на модель сессии** (`skills/roles/SKILL.md`,
   fail-closed rule).

Диагностика обязана называть fix **с его слоем** (сначала читай `_source`):
проектный id перестаёт резолвиться на чужом хосте, а голый `/roles set` пишет
user-слой, который проектный затеняет — фикс «молча» ничего не меняет. Корректные
фиксы: `/roles unset <role>` (сбросить устаревший project-оверрайд) или
`/roles set <role> <model>$<level> --project` (осознанно перепривязать проект).

Неразрешимость дефолтов на чужом хосте — это by design: ids в
`defaults/roles.md` принадлежат хост-плану автора, и потребляющий скилл тогда
останавливается с диагностикой, а не фолбэчится.
