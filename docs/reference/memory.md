# Auto-memory — тонкий MEMORY.md-указатель

Контракт долговременной памяти zcode-агента: `MEMORY.md` — только указатель,
одна строка на память; контент — в отдельных файлах рядом. Это тот же принцип,
что у самого KB («README каждой папки — её индекс», [онтология](../ontology.md)):
лёгкий указатель всегда в контексте, тяжёлый контент читается по требованию.
Память переживает сессии — и чтобы она переживала их без шума, формат здесь
дисциплина, а не вкус.

## Где живёт и чем не является

- Вне репозитория: `~/.zcode/cli/memories/projects/<слаг-проекта>/memory/` —
  персональная память агента на хосте, свой набор на проект. В git она не
  попадает: deploy-маппинги её не касаются, клон репо память не переносит.
- Не KB: движок её не индексирует и не линтит — `gitmark lint` про память
  молчит, правила ниже держит дисциплина агента (сверка — руками).
- Не хранилище секретов: значения секретов в память не пишутся никогда;
  допустим только факт «где лежит и как ротировать», без значений.

## Формат файла памяти

Одна память — один файл — один факт (не «тема»). Шаблон:

```markdown
---
name: <short-kebab-case-slug>
description: <одна строка — по ней решается релевантность при recall>
metadata:
  type: user | feedback | project | reference
---

<сам факт.>
Для feedback/project — обязательно две строки:
**Why:** <почему это правило существует>
**How to apply:** <как применять в следующих прогонах>
```

Связи с другими памятями — `[[name]]` по слагу; слаг уникален в каталоге
памяти: два файла с одним `name` делают ссылку двусмысленной. Ссылка на ещё
не записанное — не ошибка, а маркер «стоит записать». Фронтматтер хост дополняет служебными
полями (`node_type: memory`, `originSessionId`, …) — их не правим: они его.

| type | что это |
|---|---|
| `user` | кто оператор: роль, экспертиза, предпочтения |
| `feedback` | указания, как работать — исправления и подтверждённые подходы; строки `Why` и `How to apply` обязательны |
| `project` | живая работа: цели, порядок, ограничения, невыводимые из кода и git; относительные даты — в абсолютные; строки `Why` и `How to apply` обязательны |
| `reference` | указатели наружу: URL, дашборды, тикеты, внешние репо |

## MEMORY.md — указатель

`MEMORY.md` грузится в контекст **каждой** сессии — поэтому он тонкий:

- одна строка на память: `- [Заголовок](file.md) — крючок`;
- крючок — одна фраза, по которой решается «открывать ли файл»; не пересказ
  и не вторая копия факта;
- контент памяти в указатель не пишется никогда — только строка-ссылка;
- биекция «строка ↔ файл»: нет двух строк на один файл, нет строки без файла;
  обновил файл — обновил и крючок, удалил файл — удалил строку.

## Что писать, что не писать

Писать — то, чего нет в репозитории и что переживает задачу:

- решения оператора с датой (выбранная ветка дизайна, «не делать X»);
- каузалки, проверенные прогонами (глюки и обходы хоста — с evidence);
- состояние живых очередей (что отгружено, что следующим, чем закончилось);
- внешние указатели.

Не писать:

- то, что репозиторий уже фиксирует — структуру кода, прошлые фиксы, git
  history, `AGENTS.md`: дубли в памяти дрейфуют от истины и растут в шум;
- то, что живёт одну задачу или сессию — это handoff
  (`.scratch/handoff-current.md`), не память;
- значения секретов (см. выше).

Граница словами скилла handoff (`skills/handoff/SKILL.md`, шаг 5): факты
репо → репозиторий; состояние задачи → handoff-файл; переживающие задачу
факты → память.

## Гигиена

- перед записью — взгляд по указателю: обновить существующую память (файл и
  строку), а не плодить дубль;
- память оказалась неверной — переписать файл целиком или удалить его вместе
  со строкой; опровергнутая каузалка не остаётся жить рядом с новой;
- сомневаешься, память это или репозиторий — репозиторий: репо проверяемо
  (линт, тесты, ревью), память — нет.
