# 02: Гейт проходит тяжёлые файлы без провайдер-стопа

**What to build:** reviewer-ран ship-гейта на reviewer-роли user-слоя
(neuraldeep qwen) проходит дифф с тяжёлым файлом без останова «Слишком
длинный запрос» — сейчас провайдер отклоняет запрос ревьюера, когда агент
нагоняет контекст полным чтением большого файла (случаи queue-2/15 и /16;
во втором ран дошёл только ручной сменой модели оператором в GUI). Гигиена
контекста в asks гейта: ревью от диффа и адресными чтениями вместо чтения
файла целиком — паттерн одобренного оператором черновик-гейта queue-2/15,
перенесённый в вендоренный скрипт. Провайдер-стопы скрипту не видны (ран
останавливает фасад вне скрипта) — рычаг один: не порождать переполнение
контекста, не retry-логика. Качество ревью не проседает: confirm-фаза,
лимиты находок и именованное покрытие остаются как есть.

**Blocked by:** None (can start immediately).

- [x] живой прогон гейта на диффе с тяжёлым файлом (сотни строк) проходит на
      qwen3.6-35b-a3b$high без провайдер-стопа
- [x] confirm-фаза и именованное покрытие не деградировали — гейт-контракт
      вывода прежний (файлы ревью названы, находки подтверждены)
- [x] `gitmark lint` + `pytest` зелёные

**Shipping-note (2026-10-05).** Фича `370fe4a`, мерж в dev `ed44197`, релиз
v0.5.20. Оба критерия закрыты одним живым прогоном нового гейта (он же гейт
шага 6) на диффе со staged-пробой `probe-heavy-followups02.py` — 692 строки
(тикент предполагал ~400; «сотни строк» перекрыты), заведомая находка
в хвосте на 686-й строке (мутабельный дефолт `accumulated={}`). Прогон на
qwen3.6-35b-a3b$high завершился без провайдер-стопа — тот сценарий, что
останавливал раны в queue-2/15 и /16. Покрытие прежнего контракта: «в ревью
попали (4/4)» с именами; находка в глубоком хвосте найдена с воспроизведением
прогоном — адресные чтения работают; confirm 4/4 verified (все прогоны
в чекауте, 0 unconfirmed), находки только на probe — на файлах фичи
ревьюер не дал ничего, verified закрывать не требовалось. Probe снят
с индекса и удалён после приёмки, в релиз не входит. Реализация:
`contextHint(fileLines)` в аске (порог 300 строк внутри функции; до порога —
файл целиком, выше — дифф и адресные чтения по @@-заголовкам; не измерился —
тяжёлый, фейл-сейф в гигиену), размер — `wc -l` батчами по 8 (untracked уже
измерен numstat'ом, его «весь файл» и есть дифф — ветка не тронута).
contextHint — байт-в-байт копия в reviewer и code-review (тот же вектор);
матрица: 4-я функция в EXTRACT, 6 кейсов (порог/за порогом/не измерился),
построчные якоря проводки (аск с contextHint, wc-замер) и негативный якорь
на возврат безусловного «Нужен контекст — читай файл целиком»; три негатив-
пробы (возврат безусловного аска, срыв wc-замера, рассинхрон копии) ловятся
rc=1. Confirm-фаза, лимиты находок и именованное покрытие — без изменений.
