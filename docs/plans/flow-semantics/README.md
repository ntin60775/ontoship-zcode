## Goal

Планирование становится несущей конструкцией флоу: план — единственный
носитель замысла, всегда гриллован, поставляет ровно один целостный
минимально неделимый юнит функциональности с верифицируемыми критериями;
тикеты заводятся только планом; находки вне границ плана живут ишью
(файлы в git) и возвращаются планами через триаж. Очередь-парковка queue-3
упраздняется.

## Done

- **Гарантия грилла на артефакте.** Context каждого плана несёт ровно одну
  строку провенанса: след грилла (challenger-ран + дата) либо явный opt-out
  оператора с перечнем отклонённых пассов (юнит-счётчик, DoD-pass, дайджест).
  to-tickets (шаг 0/1) и ship (Input) отказывают плану без записи —
  именованный отказ, не тихий пропуск. Прецеденты «без грилла» закрываются
  как класс; единственный вход — грилл на стадии готового драфта (входы:
  /grilling, «оформи план» в разговоре, триаж ишью, перенос из других
  скиллов).
- **Юнит-семантика.** Контракт называет юнит и его план-критерии; якорь
  юнита = набор критериев план-приёмки в Done (независимо от критериев
  срезов) — некругое определение. Разбиваемость план-критериев на два
  непустых независимых набора = два юнита = грилл режет план до публикации.
  Док-планы: юнит = проверяемый артефакт знания. Эпики — ишью, не планы.
  Предикат многослайсности переписан: не «Done обещает >1 независимо
  шипуемый deliverable», а «юнит строится >1 срезом»; тест «would this ship
  as one /ship slice?» сохранён.
- **Ишью-контур.** Находка вне границ — ишью-файл
  `.zcode/ontoship/issues/NN-<slug>.md` (без frontmatter, вне KB):
  наблюдаемое поведение, источник, почему отложено; для мигрировавших
  тикетов — плюс критерии и статус. Триаж: свип открытых ишью на входе
  грилла (вход «триаж ишью») + счётчик открытых ишью в handoff-слепке.
  Жизненный цикл: при триаже содержание переезжает в контракт плана, файл
  удаляется (история в git). Правило пополнения очереди умирает.
- **Срезы — рабочие состояния.** Каждый срез обязан оставлять систему
  потребителя рабочей (норма, явно записанная в критериях срезов
  to-tickets); «independently shippable» — свойство плана (юнита), не
  тикета; промежуточные релизы срезов — штатная механика доставки.
- **План-приёмка — пост-фактум аккорд** (решение оператора 2026-10-16).
  Последний archived-тикет запускает живой прогон всех план-критериев
  юнита: зелёный → план archived; красный → план-починка (новый тикет или
  переоткрытие). Файл-планы: Goal/Done — спека среза, приёмка вырождается
  в существующее поведение — названо явно. Административная архивация
  (упразднение механизма) — именованный класс с записью причины в Context.
- **Миграция queue-3.** Тикеты 04, 05, 06 → ишью-файлы с сохранением
  содержания; план queue-3 → archived («механизм заменён ишью-контуром,
  flow-semantics»); пункт 11 «Порядка выполнения» финализирован; инвентарь
  регенерирован. Полёты проверяются живыми признаками (worktree list,
  ветки `ship/*`, незакоммиченные правки тикетов), не статусной таблицей
  README — она отстала дважды за сутки грилла (02 накануне, 03 в день
  грилла, v0.5.60).
- **Синхронность KB.** kb-curate SKILL.md (схема контракта: провенанс в
  Context, Done = план-критерии юнита) синхронен с grilling — «текст KB
  не врёт о процессе»; descriptions регенерированы инвентарём, I7 зелёная.
- checks-profile (draft, 587c631) остаётся файл-планом и прогрилливается
  перед своим шипом — первый ретро-клиент правила провенанса.
- Сьют и lint --strict зелёные; вендор `.zcode/` руками не правится
  (self-update).

### Цитаты оператора (дословно)

- «любое оформление плана не важно по какому событию подразумевает и его
  гриллинг сразу, иначе получаем неполноценный план, а также
  несоотвествие ожидаемому для оператора результату .»
- «также и с тутикетс: должно запускаться автоматом если план сложный,
  а если не нужно, то и предлоагать это незачем, иначе только вводишь
  в заблуждение оператора и заставляешь его тратить время на задавание
  тебе контрольнрыйх и наводящих вопросов, чтобы в итоге выяснить что
  тикеты здесь не нужны.»
- «тикеты в принципе не могут заводиться вне плана.»
- «все замечания и прочее что выясняется в ходе выполнения плана и что
  нельзя/не стоит править в рамках выполнения плана оформляется как ишью
  в гит»
- «и потом уже, после завершения плана или в параллельной сессии эти ишью
  анализируются и по ним оформляется план/планы.»
- «план обязан поставлять ровно один , целостный и минимально неделимый
  юнит функциональности.»
- «причём факт проверки выполнинения этого юнита всегда должен выражаться
  чётким набором критериев которые легко верифицировать для гоал флоу
  плана»
- парафраз: носитель ишью — «файлы в git» и роль приёмки — «пост-фактум
  аккорд» выбраны оператором из вариантов эскалации грилла (2026-10-16).
