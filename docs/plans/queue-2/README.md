# Контракт: очередь 2 — доставка, паритет, переезд

## Goal

Превратить ontoship-zcode из «работает у автора в сессии» в плагин, которым можно
пользоваться и переезжать: работающая установка и видимость в воркспейсе, порт
deploy-check, SessionStart-хук свежести, порт to-tickets — и только затем
подготовленный переезд потребителей с omp.

## Done

- Плагин ставится раннером маркетплейса (`deploy-plugin.py install ontoship <repo>`):
  скиллы вендорятся в `.zcode/` и видны по слэшу; runbook воспроизведён
  (`docs/ops/install.md`).
- **Самодеплой**: репозиторий плагина живёт на собственном релизе — `.zcode/skills`
  из пин-тега, работа над онтошипом идёт внутри онтошипа.
- `deploy-check.sh` валидирует вендоренную раскладку (`.zcode/skills`,
  `.zcode/defaults`, журнал): зелёный на живом деплое, честный FAIL на сломанной.
- SessionStart-хук замечает docs новее индекса и говорит об этом.
- `/to-tickets` работает в zcode и первым же прогоном разбивает хвост этой очереди.
- Хвост очереди (onto-doc, code-review/architecture, handoff/diagnose, hygiene+memory)
  размечен в тикеты нативным to-tickets.
- Migration runbook написан; пилотный полный переезд одного проекта проведён
  (аудит omp-payload → снятие → верификация).

## Scope

- Репозиторий ontoship-zcode: hooks/, scripts/deploy-check.sh, skills/to-tickets/,
  docs/ops/, самодеплой в собственный репо, правка README (guard-обещание).
- Пилотный потребительский проект — по runbook, с подтверждением оператора перед
  заменой payload.

Вне scope: порты 1c/unica плагинов omp→zcode (остаются omp-фоллбэку); MCP из
gitmark; workflow-ификация интерактива.

## Constraints

- **Переезд полный, без split-brain** (решение оператора, 2026-09-30): проект
  переезжает целиком на zcode; omp остаётся терминалом-фоллбэком для общих задач.
- **Аудит старых правил — обязательная фаза миграции**: каждый rule/skill/command
  omp-payload получает вердикт keep / drop / replace с записью в KB; значительная
  часть ожидаемо выпадает. Эквиваленты — принципы AGENTS.md и хуки, не проза-правила.
- Переезд потребителей — только после срезов 03+04 (паритет: хук + to-tickets),
  по явному подтверждению оператора на каждый проект (нативный permission-гейт).
- Runbook покрывает оба канала omp-установки (plugin remove + локальная копия);
  1c/unica omp-плагины — вне этого переезда (фоллбэк-агенту).
- Гигиена не меняет init (one-pass остаётся); sink ночных ERR — `lint --strict`
  exit-код → лог, читаемый SessionStart-хуком.
- Раннер маркетплейса пишет только код под `.zcode/`; регистрация хука и
  managed-блок — данные проекта: через post_update `say`/runbook, не раннером.

## Context

Дизайн-гриллинг 2026-09-30 (этим же репо, скилл grilling + challenger на
GLM-5.3-Flash$max; 4 существенных возражения приняты, 1 отклонена частично):

- **Порядок.** Установка/видимость + deploy-check — голова; миграция — после
  паритета, не в голове: у оператора 8 рабочих 1С-проектов с тремя omp-плагинами
  (1c + unica + ontoship), их ship-луп опирается на 1C/unica-контур; замена
  payload до паритета отрезает им правила/команды/guard (проверено challenger по
  реестрам omp).
- **Замена, не coexist.** omp native provider (priority 100) затеняет плагин (90),
  две копии дрейфуют (ontoship-omp/README.md:176–179); управляемый блок общий,
  но шаблоны у omp/zcode init разные — coexist мерцал бы блоком.
- **Guard — слой хоста.** На хостах оператора уже работает глобальный
  `~/.zcode/hooks/safety-guard.py` (PreToolUse Bash, SAFE>50/NORMAL>7,
  ZCODE_SAFETY_CONFIRM); destructive-guard из vakovalskii/destructive-guard —
  Claude Code-плагин с другим протоколом, вендор = вторая копия с несовместимым
  подтверждением. Срез вырезан; README-обещание поправлено; для guardless-хостов —
  отложено (вне очереди).
- **Тикеты: голова руками, хвост — нативным to-tickets.** MVP-папку создавал
  работавший omp-to-tickets («ручная разметка = как в MVP» — было неверно);
  хвост очереди не размечается руками — он первый приёмочный прогон порта
  to-tickets. Отступление для головы: папка создана вручную, потому что порт
  to-tickets сам является тикетом головы (в omp папку создаёт только to-tickets).
- **Гигиена/мемори в очереди, в хвосте, без init-оффера** (init — one-pass);
  зависимость от SessionStart-хука (sink ночных ERR) объявлена.
- **Канал доставки — маркетплейс `sot-zcode-marketplace`**, не глобальная
  установка zcode (политика маркетплейса: проектные плагины не ставятся
  глобально — код вендорится раннером в `<repo>/.zcode/`). `deploy.json` v1 уже
  на main (`7570688`, оператор, 2026-09-30): replace, on_drift=fail, 7 скиллов +
  defaults, post_update — пересборка индекса + 2 `say` (init managed-блока,
  проектный оверрайд ролей). Каталог пинует `ntin60775/ontoship-zcode@v0.5.1`;
  первый деплой сделан в само репо маркетплейса (журнал
  `.zcode/deployed.json` коммитится). Релиз = тег в репо плагина → правка пина →
  `update` в проектах; откат рефов раннером не поддерживается.
- **Самособой-разработка.** Репозиторий плагина сам вендорит свой последний
  релиз (`.zcode/skills` из пин-тега) — работа над онтошипом идёт внутри
  онтошипа; правки скиллов проверяются pytest+probe и доезжают релизным циклом
  (тег → пин → self-update), вендоренная копия = последний релиз, не рабочее
  дерево.

### Решение оператора (2026-09-30, закрывает open question)

Split-brain нет: проект переезжает **полностью**, всё делает zcode; omp остаётся
терминалом-фоллбэком для общих задач. Мультиплагинные 1С-проекты мигрируют по
тому же runbook (ontoship-часть); 1c/unica остаются omp-фоллбэку до собственных
портов (вне этой очереди). При первой миграции — полный контроль: аудит старых
правил с чисткой, значительная часть ожидаемо окажется лишней.
