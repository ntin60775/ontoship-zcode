# Deploy-check — валидация вендоренной раскладки

Одна команда, подтверждающая, что вендоренная копия плагина на месте и
работает — на уровне раскладки и смоуков. Запуск — из корня
**проекта-потребителя**: пакет — это `.zcode/` проекта, вендоренный раннером
по маппингам `deploy.json`; все пути резолвятся от корня проекта (git
toplevel), не от расположения скрипта.

```bash
bash .zcode/scripts/deploy-check.sh   # в проекте-потребителе (скрипт вендорится)
bash scripts/deploy-check.sh          # из чекаута репо плагина — проверяет самодеплой
```

Коды выхода: `0` — зелёный; `1` — критические проблемы (`[FAIL]`, фикс
обязателен); `2` — только предупреждения (`[WARN]`, работает с оговорками).

Проверяет:

- **Вендоренную раскладку по журналу** `.zcode/deployed.json`: ключевые файлы
  (`gitmark.py`, `roles.py`, дефолт ролей); каждая маппинг-цель из журнала на
  диске; у каждого вендоренного скилла (`mappings` → `.zcode/skills/*`) на
  месте `SKILL.md`. Журнальная запись плагина читается, `ref` печатается.
- **Роли**: вендоренный дефолт `.zcode/defaults/roles.md` валиден и содержит
  роли (парсится вендоренным же `roles.py`); `resolve --json` находит
  `reviewer` — из дефолта или проектного оверрайда.
- **SQLite**: FTS5 обязателен (`[FAIL]`), trigram-токенайзер опционален
  (`[WARN]` — заявленная деградация fuzzy/substring-поиска).
- **Движок из вендоренного пути**: `index` + смоук-поиск «OntoShip» в cwd
  проекта; ошибка движка — `[FAIL]`, пустой результат — `[WARN]` (слова может
  не быть в KB вовсе).

Не входит (и кто отвечает):

- **Пофайловая целостность и дрейф содержимого** вендоренных каталогов:
  deploy-check офлайн и без сети проверяет раскладку, не байты; расхождение
  вендора с пином ловит `deploy-plugin.py check` раннера (см. [install.md](install.md)).
- **Данные проекта** — KB, managed-блок в `AGENTS.md`, строки `.gitignore`:
  за них отвечает init-скилл (см. `post_update` в `deploy.json`).
- **omp-пути**: их нет — это zcode-порт omp-скрипта (тикет
  `../plans/queue-2/02-deploy-check.md`).
