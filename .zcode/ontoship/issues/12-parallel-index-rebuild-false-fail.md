# Параллельный rebuild индекса: ложный «не удалась» и вводящий текст ошибки

**Наблюдаемое поведение.** Два конкурентных `gitmark.py index` на одном
чекауте (два окна одной сессии, SessionStart --rebuild в обоих) не рвут
индекс — запись сериализуется транзакцией SQLite (шторм 8 писателей + 4
читателя: 7 падают с database is locked, один коммитит, integrity_check ok,
полнота среза сохраняется) — но проигравшие падают по busy-timeout с
вводящим текстом «ОШИБКА: SQLite без FTS5 (database is locked)»:
OperationalError проглатывается в `_has_trigram` (skills/kb-search/gitmark.py:394–395)
и CREATE fts (:408–410) и переклеивается в ложную диагностику отсутствия
FTS5. Через хук тот же отказ звучит как ложный msg_fail «тихая перестройка
индекса не удалась — запусти вручную», хотя ручной прогон уже идёт
параллельно. Параллельный `gitmark.py search` во время сборки падает так же.

**Источник.** Конфирмер гейта r2 шипа grilling-contracts
(dwfrun-66d28c1d, 2026-10-18) — опровержение находки о «рваном индексе»:
порча невозможна, реальный эффект — шум сообщений; шторм воспроизведён на
песочнице с 3000 md.

**Почему отложено.** Починка в движке (gitmark.py — текст ошибки и/или
busy-timeout/lock-этикет), движок вне моратория среза grilling-contracts.
Кандидаты на триаж: (а) named-ошибка busy/locked вместо подмены «без FTS5»;
(б) retry с коротким backoff в rebuild_quietly хука; (в) осознанный отказ —
шум редкий и безвредный.
